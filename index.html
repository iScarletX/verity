Verity 项目说明书 —— 它是什么、到底怎么运作、它的数字有多少能信

Verity 是一个本地、只读的审查工具，用来检查 AI 提示词（Prompt）和智能体技能包（Agent Skill）里的安全与质量问题。 这份文档按源码逐步追踪真实的审查流程，列出每一个检测器，并把项目自己测得的数字连同它的每一条限制一起摆出来—— 点击流程图中的任意方框，都能看到具体机制、对应的函数/文件，以及那一步强制遵守的安全约束。

三句话结论

是什么：一个跑在本地、不联网即可用的确定性规则审查引擎，外加一条独立、可选的实验性语义（LLM 辅助）审查通道。

现在到哪一步：确定性静态审查 = release_candidate（工程可发布）；语义审查 = 同一项目里独立的实验性功能，默认会尝试运行，但还没通过它自己定的质量门槛。

能不能信："发布"指的是工程验收（能跑、能出报告、守得住安全边界），不是精度承诺——本项目目前没有一个正式、可对外引用的"查得准不准"的数字。完整证据见下方"结果可信吗"。

第 1 章

这是什么：使命与所处阶段

Verity 要成为一个能力足够全面的审查者，覆盖 LLM Prompt 和 Agent Skill 里几乎所有能被发现的问题； 它的存在是为了超越创始人早前的工具 Butler，与 Butler 打平只是底线，不是目标。下面先说清楚"现在处在哪一阶段"。

北极星使命

Verity 的目标是成为一个能力最大化的审查者，尽可能捕捉 LLM Prompt 或 Agent Skill 中的所有问题—— 从静态检查开始，逐步扩展到动态/执行行为检查，最终被嵌入到其他智能体里，实时对被审查对象进行把关。

Butler 是创始人更早期做的工具。Verity 存在的目的是超越它——与 Butler 的检出能力打平只是 底线，不是终点。

来源：AGENTS.md §0、README.md「Mission & roadmap」

"确定性、离线"是一个阶段，不是身份

保持确定性、离线、轻依赖，是当前 V1 阶段的自律要求，用来让这个版本可发布、可复现。 这明确不是最终目标；朝着本地专用模型层、动态分析器、可嵌入服务演进，是路线图内既定的方向，不是偏离。

必须贯穿每一个阶段都不能违反的一条原则
接收不可信被审内容的核心模块，必须始终与任何模型/网络/执行层物理隔离。 新增能力的方式是扩展现有的隔离适配器模式（Bandit 和 gitleaks 已经是受控的、进程外运行的适配器）， 而不是拆掉这层隔离。

两个容易混淆的概念

检测广度（standards/ 分类体系）
回答"Verity 能多广泛地检测这一类风险？"——取值 none / signal / partial / substantial / evaluated。目前没有任何风险达到 substantial 或 evaluated。
执行状态（ReviewPlan / Execution / Coverage）
回答"这次审查里，计划要跑的检查真的跑完了吗？"——取值 completed / failed / not_enabled / not_implemented 等。
分数（0–100）
只在确定性 Coverage 足够时才出现；Critical/High/Medium/Low 各自把分数封顶在 39/59/79/99。100 只表示"已完成的检查里没有扣分项"，从不表示"100% 安全"。
安全保证
缺失或失败的关键检查不会产出任何数字分数；另有一条独立的 A–D 审查置信度等级，说明语义/剖面/广度/运行时方面的限制。等级 A 目前刻意不可达（因为 V1.5、V2 和已评测广度都还不存在）。

一次运行可以是 completed，同时检测广度仍停留在 signal——28 个语义 Finding Type 的存在，不代表语义审查已经是"完整"的。

  • 已发布的版本不含任何精度评测结论。 release_candidate 这个决定是工程验收 （工具能不能构建、运行、出报告、拦截、守住安全边界），不是精度结果。
  • 没有任何统一风险条目达到 substantial 或 evaluated 证据等级。 evaluatedLayerCount: 0，substantialOrEvaluatedLayerCount: 0 （evals/reports/v1-closure.json）。
  • 没有任何"Verity 优于或等于 Butler"的结论被授权发出。 比较器从未产出过这样的结论。
  • 项目原文（v1-closure.json）： "decision covers only the deterministic static engineering preview and its honestly-disclosed limits. It is not a claim of evaluated detection accuracy."（decision 只覆盖确定性静态工程预览版及其诚实披露的限制，不是一个已评测检出精度的结论。）
  • docs/PROGRESS.md 原文： "No claim that Verity equals or exceeds Butler is authorized."（没有任何"Verity 等于或优于 Butler"的结论被授权发出。）

来源：v1-closure.json 的 evidenceSummary。收尾报告自己把 human_expert_review_absent 列为未解决的阻塞项："AI cross-model review is not human/domain-expert review; a public production-quality claim would require the latter." （AI 交叉模型复核不是人类/领域专家复核；一个公开的生产级质量结论需要后者。）

独立标签怎么产生、又怎么"失败关闭"

  • 2 或 3 组彼此独立、各自重复的、答案隐藏的复核观测集，每组重复次数为至少 3 的奇数， 每组都要在全部计划重复中达到三分之二的决定性一致。
  • Provider 错误和不确定结果永远不计入投票。 两个明确一致的判定加一个错误算通过；一个分裂判定加一个错误算失败。
  • 两名复核者必须完全一致；三名复核者按逐案例多数决。
  • 与任一被评测系统共享配置的复核者会被拒绝（label_reviewer_configuration_not_independent）。
  • 对于隐藏留存集，盲评共识会与任何远程复核之前就已经提交的标签做比较。分歧永远不会被另一轮多数决自动消解—— 它会显式呈现为 labels_require_adjudication 并阻断结论。v5 正是这样（18 个分歧被隔离）。

后续一次 GPT-OSS/Qwen 答案隐藏诊断复核在 108/112 个案例上达成一致，其中 106 个也与预先提交的标签一致。 4 个复核者分歧和 2 个共同分歧被保留作为待裁定证据，没有被静默多数决抹掉。

3.9 什么完全没有被测量过（诚实清单）

  • 没有任何留存测试集上的精度数字存在。 v2 的封存分割集从未被消费；v3/v4/v5 全部已被消费并用于调参； v6 已冻结但未获授权进行远程观测。
  • 没有基于真实用户提示词的真实模型精度数据——语料库里每一个案例都是 verity_synthetic（合成）来源。
  • 没有延迟、成本或 token 消耗的 benchmark。 只有每次审查的调用预算上限 （64 次生成调用、128 次总校验调用、每候选 2 次校验调用），以及一份记录大小和 SHA-256 摘要的调用审计日志。
  • 没有 V1.5 或 V2 的任何测量——两者都是 not_implemented，全部 46 项风险在这两层都是 none。
  • 任何评测路径里都没有聚合安全分数。 这是刻意设计：两份语料库报告里 aggregateSafetyScore 都是 null，架构上规定评测路径不允许包含这样的分数。
  • 唯一在记录上的真实模型产品级冒烟测试（Round 61，OpenRouter，DeepSeek 做生成器、Mistral 做校验器： 在一个合成风险提示词中发现 4 个受控问题，分数 67；修正后的提示词 0 个 finding）在 PROGRESS.md 里被明确标注为 "产品路径的冒烟测试，不是精度估计"。

多模型投票的聚合算法（含打平示例）

决定性投票状态只有三种：confirmed、rejected、insufficient_evidence。 validation_failed（校验器本身出错）永远不计入多数决——这与标签复核共识协议里 "Provider 出错不投票"是同一条规则。

2 confirmed + 1 rejected
→ confirmed
2 confirmed + 1 校验失败
→ confirmed（失败票不计，运行状态不算失败）
1 confirmed + 1 rejected
→ insufficient_evidence（打平）
三种各 1 票
→ insufficient_evidence（打平）
全部校验失败
→ validation_failed

只有 confirmed 才会产出一条 Finding。 打平永远不会被悄悄地判给任何一方—— 分歧本身就是信号，说明摆在模型面前的证据没能settle这个问题，这与"所有模型都认为证据不足"是被区分记录的两种情况。

值得理解的结构性限制

确定性规则只能捕捉作者想到过的措辞

规则通过正则表达式和关键词表识别风险措辞。这是一个结构性限制，不是一次性能修好的 bug—— 这正是为什么 tools/paraphrase_coverage_probe.py 这个开发工具存在（见本轮变更）， 也是语义通道存在的原因之一。缓解设计是一套多信号精度门槛：大多数规则要求两个独立信号同时出现 （例如一个"自主授权"信号加上一个"高影响动作"信号），且在同一段文本中出现防御性/审批边界表述时 会被显式排除。

LLM 校验者不是先知

一条被确认的语义 finding 的含义是"配置的模型（们），在只看到一个候选加白名单证据加 Verity 书面判断策略的情况下， 多数认为这个可证伪问题成立"。这只是参考意见。语义 finding 只有在整个语义阶段完全完成后才会 进入分数/判定，并且每一条在 Web UI 里都会被标记为模型建议。

覆盖不足不能返回 0（成功）退出码

一次连关键检查都没能跑完的审查，不能算通过。CLI 门控在出现 High/Critical finding 时返回 1，覆盖不足（或一次配了凭证却未完成的语义运行）返回 3，配置无效返回 2。 单纯缺少 Provider 配置本身不会把一次通过的 CI 退出码翻成失败——那会惩罚那些根本没要求语义审查的用户。

一次审查 = 一个被审对象

批量扫描按规格被推迟实现。摄入上限为 500 个文件、单文件 512 KiB、总量 8 MiB。符号链接和特殊文件只作为 元数据记录，永远不会被跟随或读取；嵌套压缩包永远不会被展开。

2. 按 Finding Type 独立扫描调用 —— 注意力稀释问题的修复

症状。 针对一个真实系统提示词的真模型测试发现，25 个 Prompt 引擎语义 Finding Type 里 最多有 17 个在单次审查中产出零候选——包括那些确定性提取器已经找到真实词法种子、 指向确实存在的风险的类型。没有任何明显失败：响应通过了 schema 校验，命名的也是真实存在的 Finding Type。 它只是悄悄地停止为其中一部分类型提出候选，没有任何错误信号。

根因。 无种子的目录扫描把每一个符合条件的 Finding Type 的分类信息 打包进一次生成器调用里。在真实模型下，随着打包目录变大，这会退化—— 注意力被稀释到一次上下文中的多个并发判断任务上，模型会悄悄地少报，而不是报错。

修复。 扫描循环现在为每一个符合条件的 Finding Type 发出一次独立调用， 每次只带一个元素的 finding_catalog。调用量上升；max_candidate_generation_calls 被提高到 64，以充分覆盖完整的 28 类型目录加上有种子的调用。

同一次测试还发现了第二个 bug。 有些模型把请求自身的 subjectTaxonomy.fields 数组结构原样"回声"进了 subject 字段——例如返回 {"fields":[{"gapKind":"x"}]} 而不是要求的扁平结构 {"gapKind":"x"}。 schema 校验正确地把它拒绝为 catalog_sweep_output_violation，但真正的修复是把"必须是扁平对象" 这一要求在指令文本里明确写出来，而不是只隐含在 schema 里。记录下的经验： 当一个请求自身的 JSON 里包含一个模型不该模仿的字段列表结构时，要用文字明确说清楚——模型会照着输入的形状模式匹配。

3. 多 Provider 校验者多数决投票

  • run_review 和 SemanticOrchestrator.run 现在接受 validators=[...]（一组独立配置的 Provider）。单数形式 validator= 仍然可用，等价于单元素列表。
  • 新增 SemanticVoteRecord；SemanticAssessmentRecord 现在带有 votes 列表。新增 _aggregate_votes 实现三态多数决，打平时 vote_split → insufficient_evidence。
  • 新增 CLI 参数 --semantic-validator-vote URL,MODEL,API_KEY_ENV （可重复，最多额外 4 票；推荐总共 2–3 票、来自不同模型）。
  • 同一次改动中发现并修复的 bug： 一个被三票中两票正确确认的候选，仍会让整次运行报告 status: failed，因为某一票的临时 HTTP 错误在聚合之前就在单次调用的辅助函数里设置了 result.status。这个副作用在只有一票的旧代码里是正确的。_cast_validator_vote 现在不再因为单票失败就设置运行状态（除了真正全局性的 run_budget_exhausted）； 只有聚合结果才能决定。回归测试：test_failed_voter_does_not_count_toward_majority。

同一领域内还有：新增 --semantic-provider-kind {json_http,openai_compatible}。 大多数真实的托管 Provider 服务的是 POST {base_url}/chat/completions，不是 Verity 自定义的 /v1/verity/… 契约，所以 CLI 现在可以使用与 Web UI 相同的 OpenAI 兼容线路适配器， 配合 --semantic-max-output-tokens（默认 800）。

第三个候选被明确拒绝了——附带数字
NeMo-Guardrails 的 context_bloat_detection（Shannon 熵 + 最长连续段 + n-gram 重复率） 看起来像一个干净、无依赖的填充攻击检测器移植候选。但在一个真实场景下的安全长系统提示词 （很多条简短、措辞各异的规则）上测试，它的 3-gram 重复率是 0.69–0.87—— 远超 NeMo 自己默认的 max_repetition_ratio=0.4，且与一次真实填充攻击的 0.97–0.98 几乎重叠。一条普通的 markdown 分割线（----------）也会 触发最长连续段检查。这个移植被直接拒绝，没有带着这个问题上线，具体的量化误报证据被写了下来， 而不是悄悄跳过这个候选。现在记录下的通用规则是：移植任何开源检测器之前——即便是纯确定性的—— 都要先拿一个真实场景下的安全样本测一遍，不能只用上游项目自己的攻击样本。

5. paraphrase-coverage-probe 开发工具

新增 tools/paraphrase_coverage_probe.py（+ tests/test_paraphrase_coverage_probe.py， 10 个测试）。它专门针对"关键词规则只能捕捉作者想到过的措辞"这一结构性限制：对语料库里每个案例， 让一个 LLM 生成多个语义等价的改写，把每个改写送进真实的确定性引擎（经由 run_review）， 报告规则没能捕捉到哪些改写。人来读这些漏检并决定是否扩充关键词表。

安全属性（这个工具会向模型发送文本，所以这些约束很重要）

  • 它从不发送真实用户提交的审查内容。 它传输的唯一文本是 Verity 自己的合成语料库固定样例 （evals/corpus/v1 下）——Apache-2.0 许可、verity_synthetic 来源、 已经在仓库里公开。这条流程里没有被审对象，所以"被审内容与网络隔离"的规则没有被触及。
  • API key 从不作为命令行参数——--api-key-env 只是命名一个环境变量， 在调用时通过与产品路径相同的 ProviderCredentials 类型解析。
  • Provider 配置通过 ProviderConfig 构建，强制要求 https 或本地回环的 base URL， 并限制请求/响应大小。重定向会被拒绝。
  • 它不是产品审查路径的一部分——从未被 verity.cli、Web 应用或任何审查入口引用。 它通过公开的 run_review/intake_text API 读取规则行为， 与测试套件的做法完全一致。

实际发现和修复了什么

在 prompt.autonomy_without_approval 上发现了具体的关键词缺口，测得的改写前后对比： 留存改写命中率 0/5 → 7/10 开发诊断—— 这是对 LLM 生成的合成样例改写做的关键词覆盖探测，不是精度基准，7/10 明确不代表 "真实提示词上 70% 召回率"。

该规则需要两个独立信号同时出现（自主授权加上高影响动作），且在同一段文本中出现审批边界表述时会被抑制—— 但它的词表漏掉了常见的真实措辞。本轮新增：自主授权列表里加入 proactively|autonomously (act|work|operate|decide|execute|perform) 和 without (human|manual) (review|approval|intervention)；高影响动作列表里 加入发布/部署/上线服务/部署/发行版、发放/处理/批准退款、开启/合并pull request、 推送/提交代码或变更，以及电汇转账（包括字面工具名 execute_wire_transfer）。

6. Web UI：统一的 finding 列表

  • 原本分开的静态和语义 finding 面板合并成了一个统一的 finding 列表。 每一行带一个小的行内来源标签——确定性规则或模型建议。
  • 新增 view.py::_findings_display 负责这次合并。它纯粹是展示层函数： 计数和分数在上游、基于已经安全的 view.findings 列表计算，不受影响。它只是给每条已经计分的 finding 加一个来源标签。
  • 仅当语义运行是部分完成/不完整时，该次运行的 finding 会额外附加一个明确的 "未计入评分"标签——所以用户仍能看到它们，但不会被静默计入任何统计。 标题里的计数只使用已计分的子集。
  • 语义子区块不再重新渲染 finding，现在只保留运行诊断信息。
  • 旧的 semantic_enabled 复选框被移除——只要配置了 Provider，语义审查就会被尝试。 UI 新增了可重复添加的额外校验模型行，用于多数决投票。
  • 判定标题文案从"静态检查"改为"审查"，因为一次审查现在可能包含语义阶段。

这里保留的安全不变量：findings_view.completed_findings 只有在语义运行完全 completed 时才会包含语义 finding，所以一次不完整/失败的语义运行永远不会影响分数或通过判定—— 合并操作严格发生在这个决定之后。
