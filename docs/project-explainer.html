Section 1

Mission, and why Verity exists

The north star

Verity is being built to become a maximally-capable auditor that catches all the problems in an LLM Prompt or Agent Skill — progressing from static checks, to dynamic/execution checking, to being embedded inside other agents so it can vet artifacts in real time.

Butler was the founder's earlier tool. Verity exists to surpass it. Parity with Butler's findings is a floor, not a ceiling.

Source: AGENTS.md §0, README.md "Mission & roadmap"

"Deterministic and offline" is a phase, not the identity

Being deterministic, offline and light-dependency is the current V1-phase discipline that keeps this release shippable and reproducible. It is explicitly not the goal, and growing toward a local specialist-model layer, dynamic analyzers and an embeddable service is on-roadmap, not a deviation.

The one property that must survive every phase
The core that ingests the untrusted reviewed artifact stays physically isolated from any model, network or execution layer. New power is added by extending the existing isolated-adapter pattern (Bandit and gitleaks already run as controlled out-of-process adapters), never by dissolving that isolation.

Detection breadth is not execution status

These are two independent axes and the project keeps them apart on purpose:

  • Execution status (ReviewPlan / Execution / Coverage) answers "did the checks planned for this review run?" — words like completed, failed, not_enabled, not_implemented.
  • Detection breadth (the standards/ taxonomy) answers "how broadly can Verity detect this risk class?" — none, signal, partial, substantial, evaluated.

A run can be completed while breadth stays signal. 28 semantic Finding Types do not make semantic review complete.

Score is not a safety guarantee

A 0–100 score appears only when deterministic Coverage is sufficient. Critical/High/Medium/Low findings cap it at 39 / 59 / 79 / 99, and every deduction traces to a unified risk id and a Finding. 100 means only "no deduction in checks that actually completed" — never "100% safe". Missing or failed critical checks produce no numeric score at all.

A separate A–D review-confidence grade lists the semantic/profile/breadth/runtime limitations. Grade A is intentionally unreachable today, because V1.5, V2 and evaluated breadth are absent (scoring.py::compute_confidence).

Aggregation outcome table

Decisive votes are confirmed, rejected, insufficient_evidence. A validation_failed vote never counts toward the majority — the same "provider errors don't vote" rule the label-review consensus protocol uses.

Votes castAggregateReason codes
1× confirmedconfirmedfrom the winning vote

Only confirmed produces a Finding. A tie is never silently resolved in either direction: disagreement is itself the signal that the evidence in front of the models does not settle the question, and it is recorded distinctly from every model agreeing the evidence is insufficient.

Running it from the CLI

Semantic review is attempted by default; without complete Provider config the run honestly reports provider_not_configured and that alone does not flip a CI-facing exit code. Credentials are read only from named environment variables — never from an argument. 

export OR_KEY=...            # never passed on the command line

python3 -m verity.cli review --engine prompt --input-file p.md \
  --egress-policy redacted_evidence \
  --semantic-provider-kind openai_compatible \
  --semantic-generator-url https://openrouter.ai/api/v1 \
  --semantic-generator-model  deepseek/deepseek-chat \
  --semantic-generator-api-key-env OR_KEY \
  --semantic-validator-url https://openrouter.ai/api/v1 \
  --semantic-validator-model  mistralai/mistral-large \
  --semantic-validator-api-key-env OR_KEY \
  --semantic-validator-vote https://openrouter.ai/api/v1,qwen/qwen-2.5-72b-instruct,OR_KEY \
  --semantic-validator-vote https://openrouter.ai/api/v1,openai/gpt-4o-mini,OR_KEY

# skip semantic review entirely:
python3 -m verity.cli review --engine prompt --input-file p.md --no-semantic

Each --semantic-validator-vote adds one more independent Validator (repeatable, up to 4 extra on top of the required primary). 2–3 total votes across different models is the recommended range. Distinct role-bound Provider objects are constructed per vote even when two votes share an endpoint, so no client shares state across votes.

Source: v1-closure.json evidenceSummary. The closure report lists human_expert_review_absent as an open blocker in its own words: "AI cross-model review is not human/domain-expert review; a public production-quality claim would require the latter."

How independent labels are derived (and how they fail closed)

  • 2 or 3 distinct, independently repeated answer-hidden reviewer observation sets, each with an odd repetition count of at least 3, each reaching two-thirds decisive consensus across all planned repetitions.
  • Provider errors and inconclusive results never vote. Two explicit matching decisions plus one error passes; a split decision plus one error fails.
  • Two reviewers must agree exactly; three use per-case majority.
  • Reviewer configurations shared with either evaluated system are refused (label_reviewer_configuration_not_independent).
  • For hidden holdouts, blind consensus is compared with the labels committed before any remote review. A disagreement is never auto-resolved by another majority — it surfaces as labels_require_adjudication and blocks the claim. This is exactly what happened to v5 (18 disagreements quarantined).

A later GPT-OSS/Qwen answer-hidden diagnostic agreed on 108/112 cases, with 106 also matching the precommitted labels. The 4 reviewer disagreements and 2 shared disagreements were retained as evidence for rewriting/adjudication, not silently majority-voted away.

5.7 What is not measured anywhere

  • No held-out accuracy figure exists. v2's sealed split is unconsumed; v3/v4/v5 are all consumed and tuned-on; v6 is frozen but unauthorized for remote observation.
  • No real-model accuracy on real user prompts — every corpus case is verity_synthetic.
  • No latency, cost, or token benchmark. Only per-review call budgets exist (64 generation calls, 128 total validation calls, 2 validation calls per candidate), plus a payload audit recording sizes and SHA-256 digests.
  • No V1.5 or V2 measurement — both are not_implemented, and all 46 risks are none at those layers.
  • No aggregate safety score in any evaluation path. Deliberate: aggregateSafetyScore: null in both corpus reports, and the architecture states no evaluation path may contain one.
  • The one real-model product smoke test on record (Round 61, OpenRouter with a DeepSeek generator and Mistral validator: 4 controlled problems found in a synthetic risky prompt, score 67, 0 findings on the corrected prompt) is labelled in PROGRESS.md as "a product-path smoke test, not an accuracy estimate."

Structural limits worth understanding

Deterministic rules only catch wording their author thought of

Rules recognise risk phrasing via regex and keyword tables. This is a structural limit, not a bug to be patched once — it is why the tools/paraphrase_coverage_probe.py dev tool exists (see the session changelog) and why the semantic track exists at all. The mitigating design is a multi-signal precision gate: most rules require two independent signals (e.g. an autonomy mandate and a high-impact action) with an explicit exclusion for a defensive/approval boundary in the same text.

An LLM validator is not an oracle

A confirmed semantic finding means "the configured model(s), shown one candidate plus whitelisted evidence and Verity's written judgment policy, said the falsification question resolves against the artifact by majority". It is advisory. Semantic findings enter score/gate only when the whole semantic stage completed, and every one of them is tagged as model-suggested in the Web UI.

Coverage-insufficient must not exit zero

A review that could not run its critical checks is not a pass. The CLI gate returns 1 on High/Critical findings, 3 on insufficient coverage (or a credentialed semantic run that did not complete), 2 on invalid configuration. A missing Provider config alone does not flip a passing CI exit code to failing — that would punish users who never asked for semantic review.

One Review = one Artifact

Batch scanning is deferred by spec. Intake is bounded at 500 files, 512 KiB per file, 8 MiB total. Symlinks and special files are recorded as metadata and never followed or read; nested archives are never expanded.

This session's changes (round 67, working tree)

Status of this section
Written against the uncommitted working tree at the time of writing: 35 modified tracked files (+2,536 / −640 lines) plus 4 new corpus case directories, a new dev tool, a new test module and a new mining-notes document. The last commit is 9c9ad2b ("Round 66: close audit integrity gaps"), so none of the below is in git history yet and the verified_against test count (786) predates it.

1. Semantic review flipped to attempted-by-default

  • SemanticConfig.enabled now defaults to True and egress_policy defaults to redacted_evidence (previously off, which refused to pair with enabled=True).
  • The CLI --semantic flag became argparse.BooleanOptionalAction with default=True; the new --no-semantic skips semantic review entirely.
  • The CI gate was corrected in the same move: _gate_from_report now takes semantic_requires_pass (i.e. "did the caller hand this run real credentials") instead of semantic_requested. An unconfigured Provider honestly reporting provider_not_configured no longer flips a passing exit code to 3.
  • Report and HTML wording updated to "attempted by default when a Provider is configured (experimental, unevaluated accuracy)". The accuracy claim did not change at all — closure.py still carries semantic_review_experimental_quality_unproven and the track is still inReleaseGate: false.

2. Per-Finding-Type independent sweep calls — the attention-dilution fix

Symptom. Real-model testing against a realistic system prompt found up to 17 of 25 prompt-engine semantic Finding Types producing zero candidates in a single review — including types whose deterministic extractor had a real lexical seed pointing at a genuine risk. Nothing failed loudly: the response validated against schema and named real Finding Types. It simply stopped proposing for a subset, with no error signal.

Root cause. The no-seed catalog sweep packed every sweep-eligible Finding Type's taxonomy into one generator call. Under a real model this degrades as the packed catalog grows — attention is diluted across many simultaneous judgment tasks in one context and the model quietly under-reports.

Fix. The sweep loop now issues one independent call per sweep-eligible Finding Type, each receiving a single-entry finding_catalog. Call volume rises; max_candidate_generation_calls was raised to 64 to comfortably cover the full 28-type catalog plus seeded calls.

A second bug the same testing surfaced. Some models echoed the request's own subjectTaxonomy.fields array shape back into subject — e.g. {"fields":[{"gapKind":"x"}]} instead of the required flat {"gapKind":"x"}. Schema validation correctly rejected it as catalog_sweep_output_violation, but the real fix was making the flat-object requirement explicit in the instruction text rather than leaving it implicit in the schema. Lesson recorded: when a request's own JSON contains a field-list structure the model must not imitate, say so in words — models pattern-match on input shape.

3. Multi-Provider Validator majority voting

  • run_review and SemanticOrchestrator.run accept validators=[...] (a list of independently configured Providers). validator= singular still works and is equivalent to a one-element list.
  • New SemanticVoteRecord; SemanticAssessmentRecord now carries a votes list. New _aggregate_votes implements three-state majority with vote_split → insufficient_evidence on a tie.
  • New CLI flag --semantic-validator-vote URL,MODEL,API_KEY_ENV (repeatable, up to 4 extra votes; 2–3 total across different models recommended).
  • Bug found and fixed within the same change: a candidate that two of three voters correctly confirmed still made the whole run report status: failed, because one voter's transient HTTP error set result.status inside the per-call helper before aggregation. That per-vote side effect was correct when there was only ever one vote. _cast_validator_vote no longer sets run status on a per-vote failure (except a genuine run_budget_exhausted, which really is global); only the aggregate decides. Regression test: test_failed_voter_does_not_count_toward_majority.

Also in this area: --semantic-provider-kind {json_http,openai_compatible}. Most real hosted providers serve POST {base_url}/chat/completions, not Verity's custom /v1/verity/… contract, so the CLI can now use the same OpenAI-compatible wire adapter the Web UI uses, with --semantic-max-output-tokens (default 800).

A third candidate was deliberately rejected — with numbers
NeMo-Guardrails' context_bloat_detection (Shannon entropy + longest-run + n-gram repetition) looked like a clean dependency-free port for a padding-attack detector. Measured against a realistic safe long system prompt (many short, differently-worded bullet rules), its 3-gram repetition ratio was 0.69–0.87 — well past NeMo's own default max_repetition_ratio=0.4, and essentially overlapping with a genuine padding attack's 0.97–0.98. An ordinary markdown horizontal rule (----------) also trips the longest-run check. The port was rejected rather than shipped broad, and the specific quantitative false-positive evidence was written down instead of silently skipping the candidate. The general rule now: before porting any OSS detector — even fully deterministic — run it against a realistic SAFE fixture, not just the upstream project's attack examples.

5. The paraphrase-coverage-probe dev tool

New tools/paraphrase_coverage_probe.py (+ tests/test_paraphrase_coverage_probe.py, 10 tests). It attacks the structural limit that a keyword rule only catches wording its author thought of: for each corpus case it asks an LLM for many meaning-preserving paraphrases of the already-public synthetic positive example, runs every paraphrase through the real deterministic engine via run_review, and reports which paraphrases the rule failed to catch. A human then reads the misses and decides whether to extend the keyword table.

Safety properties (this tool sends text to a model, so they matter)

  • It never sends real user-submitted review content. The only text it transmits is Verity's own synthetic corpus fixtures under evals/corpus/v1 — Apache-2.0, verity_synthetic provenance, already public in the repository. There is no reviewed artifact in this flow, so the "reviewed artifact stays isolated from the network" rule is not touched.
  • The API key is never a CLI argument — --api-key-env names an environment variable, resolved at call time through the same ProviderCredentials type the product path uses.
  • Provider config is built with ProviderConfig, which enforces https-or-loopback base URLs and bounded request/response sizes. Redirects are refused.
  • It is not part of the product review path — never imported by verity.cli, the web app, or any review entry point. It reads rule behaviour through the public run_review/intake_text APIs, exactly as the test suite does.

What it actually found and fixed

Concrete keyword gaps in prompt.autonomy_without_approval. The rule needs two independent signals (an autonomy mandate and a high-impact action) and is suppressed by an approval boundary in the same text — but its vocabulary missed common real phrasings. Added this session: to the autonomy mandate list, proactively|autonomously (act|work|operate|decide|execute|perform) and without (human|manual) (review|approval|intervention); to the high-impact action list, publishing/deploying/releasing services / deployments / releases, issuing/processing/approving refunds, opening/merging pull requests, pushing/committing code or changes, and wire transfers (including the literal tool name execute_wire_transfer).

6. Web UI: one unified findings list

  • The separate static and semantic findings panels were merged into one findings list. Each row carries a small inline origin tag — 确定性规则 (deterministic rule) or 模型建议 (model-suggested).
  • New view.py::_findings_display performs the merge. It is purely a display-layer function: counts and score are computed upstream from the already-safe view.findings list and are not affected. It only adds an origin tag to each already-scored finding.
  • For a partial/incomplete semantic run only, that run's findings are additionally appended with an explicit "未计入评分" (not scored) badge — so the user still sees them without them silently counting anywhere. The heading count uses only the scored subset.
  • The semantic sub-block no longer re-renders findings; it now holds run diagnostics only.
  • The old semantic_enabled checkbox is gone — semantic review is attempted whenever a Provider is configured. The UI gained repeatable extra validator-model rows for majority voting.
  • Verdict headline wording changed from "静态检查" (static check) to "审查" (review), since a review may now include the semantic stage.

The safety invariant preserved here: findings_view.completed_findings only ever includes semantic findings when the semantic run fully completed, so an incomplete/failed semantic run can never affect score or pass verdict — the merge happens strictly downstream of that decision.
