Verity 中文交互式完整说明书

这是一份从“它是不是 Agent”一直讲到源码、报告字段和故障排查的总手册。Verity 本身不是通用 Agent，也不是搭建 Agent 的框架；它是一个本地 Prompt / Agent Skill 审查器与证据工作台。你可以按使用场景阅读，也可以直接搜索问题、 命令、风险编号或源码路径。每项能力都会同时说明：能做什么、默认是否运行、是否联网、能证明什么，以及不能证明什么。

三句话结论

是什么：一个默认可在本地完成静态审查的 Prompt / Skill 审查器，外加受信任调用方才能配置的实验性语义、Prompt 黑盒和 CLI-only Agent Harness。可执行 Skill 产品沙箱当前不可用，显式请求也会失败关闭。

现在到哪一步：确定性静态审查 = release_candidate（工程可发布）；语义审查 = 同一项目里独立的实验性功能，默认会尝试运行，但还没通过它自己定的质量门槛。

能不能信："发布"指的是工程验收（能跑、能出报告、守得住安全边界），不是精度承诺——本项目目前没有一个正式、可对外引用的"查得准不准"的数字。完整证据见下方"结果可信吗"。

30 秒答法：Verity 是 Agent 吗？
不是。Verity 是审查 Prompt 和 Agent Skill 的工具。它可以检查一个 Agent 的提示词、Skill 包和有界运行信号， 但它不负责替你持续对话、编排业务工具或搭建 Agent。外部 DeepSeek Harness 只是它可选使用的一条实验性适配器路径。
第一次使用 · 约 5 分钟

从安装到第一份报告

需要 Python >=3.9,<3.14。普通用户推荐本地 Evidence Console；自动化与高级动态配置使用 CLI。

创建虚拟环境并安装固定依赖

python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install --upgrade pip setuptools wheel
pip install -r requirements.lock
pip install -e .

开发和测试再安装 requirements-dev.lock。所有命令都应在仓库根目录运行。

安装固定版本 gitleaks

python3 tools/install_gitleaks.py

Web 的 Skill 审查固定使用 standard profile，gitleaks 是关键检查。缺失、版本不符或二进制哈希漂移都会让 Coverage 不足；系统不会悄悄降级并声称没有 Secret。

启动本地 Evidence Console

python3 tools/start_local_web.py

浏览器默认打开 http://127.0.0.1:8765/。也可双击 start-verity.command，或用 --port 9000 换端口。服务拒绝 0.0.0.0 等非 loopback 地址。

选择 Prompt 或 Skill

检查 Prompt

  1. 粘贴文本或载入 .txt/.md/.json。
  2. 选择 user_prompt 或 system_prompt。
  3. 若只想本地静态检查，不配置 Provider、不启用黑盒。
  4. 点击“开始审查”。

检查 Agent Skill

  1. 选择本地文件夹，或上传一个 .zip。
  2. Web 支持单个 Skill ZIP，会检查路径穿越、条目冲突和解压预算。
  3. CLI 仍只接受 Skill 文件夹，不直接接 ZIP。
  4. 当前 Skill 执行沙箱禁用；静态规则、Bandit、gitleaks 仍正常运行。

需要自动化时使用 CLI

python3 -m verity.cli review --engine prompt \
  --prompt-kind user_prompt --input-file prompt.txt --out out/prompt

python3 -m verity.cli review --engine skill \
  --profile standard --input-dir ./my-skill --out out/skill

每次 CLI 审查写出 report.json、report.html 和 report.sarif。退出码 0/1/3 分别对应 pass、High/Critical 阻断、Coverage/请求阶段未完成；参数错误由 argparse 返回 2。

读结果、下载、停止

先看 Verdict 与 Coverage，再看统一 Issues、Finding 证据、动态计划和整改建议。Web 报告链接存在进程内 TTL/LRU 中，服务器重启后会失效；需要长期保存就下载报告文件。停止服务时回到启动它的终端按 Ctrl+C。

说明书服务器不是审查服务：如果只想交互阅读本页，可运行 python3 -m http.server 8766 --bind 127.0.0.1 --directory docs；它只监听本机回环地址，不会启动 Verity API。

第 1 章

这是什么：使命与所处阶段

Verity 要成为一个能力足够全面的审查者，覆盖 LLM Prompt 和 Agent Skill 里几乎所有能被发现的问题； 它的存在是为了超越创始人早前的工具 Butler，与 Butler 打平只是底线，不是目标。下面先说清楚"现在处在哪一阶段"。

北极星使命

Verity 的目标是成为一个能力最大化的审查者，尽可能捕捉 LLM Prompt 或 Agent Skill 中的所有问题—— 从静态检查开始，逐步扩展到动态/执行行为检查，最终被嵌入到其他智能体里，实时对被审查对象进行把关。

Butler 是创始人更早期做的工具。Verity 存在的目的是超越它——与 Butler 的检出能力打平只是 底线，不是终点。

来源：AGENTS.md §0、README.md「Mission & roadmap」

"确定性、离线"是一个阶段，不是身份

保持确定性、离线、轻依赖，是当前 V1 阶段的自律要求，用来让这个版本可发布、可复现。 这明确不是最终目标；朝着本地专用模型层、动态分析器、可嵌入服务演进，是路线图内既定的方向，不是偏离。

必须贯穿每一个阶段都不能违反的一条原则
接收不可信被审内容的核心模块，必须始终与任何模型/网络/执行层物理隔离。 新增能力的方式是扩展现有的隔离适配器模式（Bandit 和 gitleaks 已经是受控的、进程外运行的适配器）， 而不是拆掉这层隔离。

两个容易混淆的概念

检测广度（standards/ 分类体系）
回答"Verity 能多广泛地检测这一类风险？"——取值 none / signal / partial / substantial / evaluated。目前没有任何风险达到 substantial 或 evaluated。
执行状态（ReviewPlan / Execution / Coverage）
回答"这次审查里，计划要跑的检查真的跑完了吗？"——取值 completed / failed / not_enabled / not_implemented 等。
分数（0–100）
只在确定性 Coverage 足够时才出现；Critical/High/Medium/Low 各自把分数封顶在 39/59/79/99。100 只表示"已完成的检查里没有扣分项"，从不表示"100% 安全"。
安全保证
缺失或失败的关键检查不会产出任何数字分数；另有一条独立的 A–D 审查置信度等级，说明语义/剖面/广度/运行时方面的限制。等级 A 目前刻意不可达，因为目前仍没有已评测的检测广度；能运行动态检查并不等于已证明准确率。

一次运行可以是 completed，同时检测广度仍停留在 signal——41 个语义 Finding Type 的存在，不代表语义审查已经是"完整"的。

  2. 构造确定性 ReviewPlan。

架构 · 点击信任区看数据

系统架构与数据流：什么留在本机，什么可能出站

架构的核心不是“所有东西都离线”，而是每条跨边界路径都必须由受信任调用方开启、按最小投影传输，并且不能让被审 Artifact 配置审查环境。

不可信输入区

职责：把一个 Prompt 或 Skill 变成受预算约束的内存快照。Skill 目录拒绝逃逸路径并不跟随符号链接；Web ZIP 还拒绝重复/大小写冲突路径并按实际增量读取计数。

红线：被审内容不能选择 Provider、模型、凭证、出站策略、严重度、Scenario、预算、工具路径或沙箱开关。

源码：src/verity/intake.py、src/verity/web/app.py::_extract_skill_zip。

  • Skill 沙箱卡解释隔离缺口且不可启用；伪造表单也只会失败关闭。
  • Bandit/gitleaks 是受信任分析器 subprocess，不等于执行被审 Skill。

语义 Provider

  • 配置 OpenAI-compatible base URL、API Key、Candidate 模型和 Validator 模型。
  • 可增加独立 Validator，总票数推荐 2–3；平票成为 insufficient_evidence。
  • 保存设置时，Key 进入 Keychain；页面不会读回明文。
  • 没配完整 Provider 时，语义内部状态为 provider_not_configured，报告能力投影为 failed；这本身不自动阻断 CLI。

结果画布

  • 先读 Verdict、Coverage、Score 与 Confidence，不要只看一个数字。
  • 统一 Issues 按风险聚合静态、语义、黑盒和运行时 occurrence。
  • 源码工作台用 byte range 定位 Evidence；Secret 预览保持脱敏。
  • 修复工作台只改 Prompt 草稿并重新审查，或给出 Skill 建议；没有自动 Patch 应用。
  • 可下载 JSON、HTML、SARIF，并查看动态计划与诊断原因码。

报告参考 · 先分清四个结论

如何读懂 JSON / HTML / SARIF 报告

Coverage
回答“计划中的关键检查完成了吗？”不足时不能给乐观主体 Verdict，也没有数字 Score。
Verdict
回答“在当前证据和覆盖下，该 Prompt/Skill 该如何处置？”与 CLI 是否阻断不是完全同一件事。
Score
0–100 的可解释扣分投影。100 只表示已完成检查里没有扣分，不表示 100% 安全。
Review Confidence
A–D 的结论可信度。A 当前不可达；它不等于安全分，也不表示模型信心。

顶层字段词典

reviewId / engine
一次审查的高熵标识和对象类型（prompt / skill）。它们不等于 Skill 项目身份。
snapshot
Artifact 快照的内容摘要、文件元数据与摄入状态。下游不回读原目录。
plan / executions
确定性计划及每项真实状态：completed、not_applicable、failed、blocked_by_upstream_failure 等。
coverage
计划是否充分完成、关键 gap 和 policy id。缺口不是“没发现问题”，而是“没有完成检查”。
evidences / ruleMatches / findings
字节事实 → 规则命中事件 → 可报告问题。Finding 的严重度由本地规则/目录决定。
behaviorProfile
任务、runtime kind、输入输出、工具、状态、副作用、敏感数据和外部内容事实；它本身不是漏洞。
dynamicPlan
每个动态检查为何 selected、not_applicable 或 unavailable。selected 只代表值得运行，不代表已执行或通过。
artifactModel
解析器/能力提取形成的受控 Artifact 结构，供后续规则和语义阶段使用。
semantic（条件字段）
只在构造了语义运行结果时出现：受控语义计划、调用审计、候选评估和确认 Finding。只有阶段完整完成的确认 Finding 才进入正式投影。
promptBlackbox（条件字段）
只在 Prompt 黑盒被请求并形成运行结果时出现：Scenario 选择、受控结果与运行摘要；公开投影不保留原 Prompt、probe 或 Provider response。
skillSandbox（条件字段）
只在 Skill 沙箱被显式请求时出现；当前产品路径投影为 failed / observation unavailable，并给出 sandbox_isolation_hardening_required。
agentInstructionRuntime（条件字段）
只在 CLI 受信任调用方提供 Harness 配置时出现：有界场景和 attempt signals；完成不代表 OS 隔离或 Agent 安全。
capabilities（始终存在）
static、semantic、promptBlackbox、skillSandbox、agentInstructionRuntime 五维状态账本。五项始终都有状态；其中 static 可为 completed 或 failed，其余未请求时为 not_enabled。
score
按统一风险和严重度做递减扣分，Critical/High/Medium/Low 分数上限分别为 39/59/79/99；覆盖不足时 unavailable。
reviewConfidence
说明静态、语义、画像、动态与 breadth 限制；始终披露 capability_breadth_not_evaluated。
remediations
按优先级给出 actions 和同范围复查项；applyMode=proposal_only，不会自动修改文件。
issues
按稳定风险 ID 聚合多层 occurrence，但保留所有来源身份和证据。
verdict
Coverage、主体处置、原因码和 policy。Prompt 有 Finding 通常 needs_revision；Skill 依严重度为 do_not_install/review_required/low_detected_risk。
owaspCoverage（Skill）
Skill 风险到 OWASP Agentic/相关控制的映射视图；不是额外检测器。

独立标签怎么产生、又怎么"失败关闭"

  • 2 或 3 组彼此独立、各自重复的、答案隐藏的复核观测集，每组重复次数为至少 3 的奇数， 每组都要在全部计划重复中达到三分之二的决定性一致。
  • Provider 错误和不确定结果永远不计入投票。 两个明确一致的判定加一个错误算通过；一个分裂判定加一个错误算失败。
  • 两名复核者必须完全一致；三名复核者按逐案例多数决。
  • 与任一被评测系统共享配置的复核者会被拒绝（label_reviewer_configuration_not_independent）。
  • 对于隐藏留存集，盲评共识会与任何远程复核之前就已经提交的标签做比较。分歧永远不会被另一轮多数决自动消解—— 它会显式呈现为 labels_require_adjudication 并阻断结论。v5 正是这样（18 个分歧被隔离）。

后续一次 GPT-OSS/Qwen 答案隐藏诊断复核在 108/112 个案例上达成一致，其中 106 个也与预先提交的标签一致。 4 个复核者分歧和 2 个共同分歧被保留作为待裁定证据，没有被静默多数决抹掉。

  • 没有任何留存测试集上的精度数字存在。 v2 的封存分割集从未被消费；v3/v4/v5 全部已被消费并用于调参； v6 已冻结但未获授权进行远程观测。
  • 没有基于真实用户提示词的真实模型精度数据——语料库里每一个案例都是 verity_synthetic（合成）来源。
  • 没有延迟、成本或 token 消耗的 benchmark。 只有每次审查的调用预算上限 （64 次生成调用、128 次总校验调用、每候选 2 次校验调用），以及一份记录大小和 SHA-256 摘要的调用审计日志。

决定性投票状态只有三种：confirmed、rejected、insufficient_evidence。 validation_failed（校验器本身出错）永远不计入多数决——这与标签复核共识协议里 "Provider 出错不投票"是同一条规则。

2 confirmed + 1 rejected
→ confirmed
2 confirmed + 1 校验失败
→ confirmed（失败票不计，运行状态不算失败）
1 confirmed + 1 rejected
→ insufficient_evidence（打平）
三种各 1 票
→ insufficient_evidence（打平）
全部校验失败
→ validation_failed

值得理解的结构性限制

确定性规则只能捕捉作者想到过的措辞

规则通过正则表达式和关键词表识别风险措辞。这是一个结构性限制，不是一次性能修好的 bug—— 这正是为什么 tools/paraphrase_coverage_probe.py 这个开发工具存在（见本轮变更）， 也是语义通道存在的原因之一。缓解设计是一套多信号精度门槛：大多数规则要求两个独立信号同时出现 （例如一个"自主授权"信号加上一个"高影响动作"信号），且在同一段文本中出现防御性/审批边界表述时 会被显式排除。

LLM 校验者不是先知

一条被确认的语义 finding 的含义是"配置的模型（们），在只看到一个候选加白名单证据加 Verity 书面判断策略的情况下， 多数认为这个可证伪问题成立"。这只是参考意见。语义 finding 只有在整个语义阶段完全完成后才会 进入分数/判定，并且每一条在 Web UI 里都会被标记为模型建议。

覆盖不足不能返回 0（成功）退出码

一次连关键检查都没能跑完的审查，不能算通过。CLI 门控在出现 High/Critical finding 时返回 1，覆盖不足（或一次配了凭证却未完成的语义运行）返回 3，配置无效返回 2。 单纯缺少 Provider 配置本身不会把一次通过的 CI 退出码翻成失败——那会惩罚那些根本没要求语义审查的用户。

一次审查 = 一个被审对象

批量扫描按规格被推迟实现。摄入上限为 500 个文件、单文件 512 KiB、总量 8 MiB。符号链接和特殊文件只作为 元数据记录，永远不会被跟随或读取；嵌套压缩包永远不会被展开。

常见问题为什么发生、该怎么处理

浏览器显示 ERR_CONNECTION_REFUSED
该端口没有进程监听。回到仓库根目录运行 python3 tools/start_local_web.py；若你打开的是说明书端口 8766，请确认静态服务器仍在运行。不要把 8765 的 Evidence Console 和 8766 的说明书静态服务器混在一起。
port 127.0.0.1:8765 is already in use
换用 python3 tools/start_local_web.py --port 9000，或自行停止占用方。启动器不会 kill 其它进程，也不会后台留守。
refusing to bind non-loopback host

Provider 配好了但语义/黑盒仍失败

Skill ZIP 被拒绝

之前的 Web 报告 URL 失效
普通报告存在进程内 LRU/TTL，重启服务器会让全部 URL 失效。需要留档时下载 JSON/HTML/SARIF；Skill 项目历史是另一套持久化安全投影。
请求 Skill 沙箱得到 sandbox_isolation_hardening_required
这是当前设计的成功失败关闭：系统在构造旧 research runner 前拒绝执行。没有配置能把它变成可用产品能力；需要等待 host-read、输出/磁盘/进程树、观察器和清理边界完成独立加固。
Agent Harness 报配置不完整或版本/哈希错误
必须提供 Node 和 DSH JavaScript 入口的绝对路径与 SHA-256、DSH 0.1.1-rc.2、Provider URL/模型、API Key 环境变量名。入口在私有快照中校验并执行；相邻 npm 闭包仍不在这两个哈希认证范围内。

2. 按 Finding Type 独立扫描调用 —— 注意力稀释问题的修复

症状。 针对一个真实系统提示词的真模型测试发现，25 个 Prompt 引擎语义 Finding Type 里 最多有 17 个在单次审查中产出零候选——包括那些确定性提取器已经找到真实词法种子、 指向确实存在的风险的类型。没有任何明显失败：响应通过了 schema 校验，命名的也是真实存在的 Finding Type。 它只是悄悄地停止为其中一部分类型提出候选，没有任何错误信号。

根因。 无种子的目录扫描把每一个符合条件的 Finding Type 的分类信息 打包进一次生成器调用里。在真实模型下，随着打包目录变大，这会退化—— 注意力被稀释到一次上下文中的多个并发判断任务上，模型会悄悄地少报，而不是报错。

修复。 扫描循环现在为每一个符合条件的 Finding Type 发出一次独立调用， 每次只带一个元素的 finding_catalog。调用量上升；max_candidate_generation_calls 被提高到 64，以充分覆盖完整的 28 类型目录加上有种子的调用。

同一次测试还发现了第二个 bug。 有些模型把请求自身的 subjectTaxonomy.fields 数组结构原样"回声"进了 subject 字段——例如返回 {"fields":[{"gapKind":"x"}]} 而不是要求的扁平结构 {"gapKind":"x"}。 schema 校验正确地把它拒绝为 catalog_sweep_output_violation，但真正的修复是把"必须是扁平对象" 这一要求在指令文本里明确写出来，而不是只隐含在 schema 里。记录下的经验： 当一个请求自身的 JSON 里包含一个模型不该模仿的字段列表结构时，要用文字明确说清楚——模型会照着输入的形状模式匹配。

Verity 是一个和 Codex 一样的 Agent 吗？

不是。Verity 是 Prompt / Agent Skill 审查器与证据工作台。

它检查已有 Prompt、Skill 包和有界运行信号，不负责持续对话、规划任务或替用户调用业务工具。未来“嵌入其它 Agent 实时把关”仍是路线图。

可以用 Verity 搭建一个 Agent 吗？

不能直接搭建；它负责检查你已经写好的 Agent Prompt 或 Skill。

Agent 的编排、记忆、工具、部署由其它框架完成，Verity 的价值是发现契约、安全、依赖、权限和运行行为风险。

DeepSeek Harness 就是 Verity 吗？

不是。DSH 是 Verity 可选接入的一条外部 Agent 指令运行时。

可以监听 0.0.0.0 给别人访问吗？

不可以，服务端会拒绝非 loopback 绑定。

本地 Web 同时检查 Host 和 Origin；若要做远程服务，需要独立设计认证、授权、隔离和安全评审，当前没有隐藏开关。

Prompt 可以怎么输入？

Web 可粘贴或读取文本文件；CLI 可用 --text 或 --input-file。

单个 Prompt 上限 256 KiB，拒绝 NUL；必须声明 user_prompt 或 system_prompt。

为什么 Prompt 要区分 user 和 system？

因为权限、Secret 和工具授权等规则只对 system prompt 有意义。

不适用于 user prompt 的规则不会静默消失，而是以带原因的 not_applicable 记录在计划中。

Skill 可以上传文件夹吗？

可以。Web 用目录选择器，CLI 用 --input-dir。

摄入会冻结内存快照，不跟随符号链接，并对文件数量和大小做预算。

Skill 可以上传 ZIP 吗？

普通 Web Skill 审查支持一个 ZIP；CLI 仍只支持目录。

ZIP 会检查 zip-slip、绝对路径、反斜杠、NUL、重复/大小写冲突、条目与实际解压预算；项目历史的新增版本接口仍是文件夹上传。

可以直接填 GitHub URL 审查吗？

不可以，GitHub URL 摄入尚未实现。

先可信地克隆或下载到本地，再选择目录/ZIP。Verity 不会把外部仓库 URL 当作可自动抓取的指令。

一次可以批量审查多个 Artifact 吗？

不可以；一次 Review 对应一个 Prompt 或一个 Skill。

需要批处理时由调用方逐个调用 CLI，并保留每个 Artifact 独立的 Snapshot、Coverage 与报告身份。

Skill 摄入预算是多少？

最多 500 个文件、单文件 512 KiB、总量 8 MiB。

Web multipart 外层还有 12 MiB 请求上限；超限是可见失败，不会抽样后假装审查完整。

支持哪些编程语言？

Python 有 AST/Bandit 级分析；Shell、JS、TS、Ruby、Go 等目前主要是文本信号。

看见某语言后缀不等于拥有完整数据流分析，报告的 breadth 会诚实保持 signal/partial。

为什么要单独安装 gitleaks？

standard Skill profile 把真实 Secret 扫描作为关键检查。

Verity 固定 gitleaks 8.28.0 的下载和二进制哈希；启动器不会自动安装，缺失会令 Coverage insufficient。

一次审查输出什么？

CLI 固定输出 report.json、report.html、report.sarif。

Web 可下载同三种格式；HTML 是转义后的单文件报告，SARIF 2.1.0 供代码扫描消费者使用。

核心流程与静态证据

审查第一步发生什么？

安全摄入一个 Artifact，并冻结为内存快照。

路径、类型、数量、大小与读取竞态先被约束；失败就停止，不会把半截内容送进后续阶段。

ArtifactSnapshot 是什么？

一次内容寻址、不可变的被审对象快照。

它记录文件元数据和 digest；下游使用冻结的 file_bytes，不再直接读取用户目录。

ReviewPlan 是什么？

本次确定性审查应该执行哪些 Parser、Analyzer 和规则的账本。

每项有适用性、门控和最终执行状态；Coverage 正是拿计划与执行结果对账。

not_applicable 是失败吗？

不是，只要有注册表给出的明确适用性原因。

例如 system-only 规则在 user prompt 中不适用；这种透明跳过可以满足计划，不等同于漏跑。

blocked_by_upstream_failure 是通过吗？

不是，表示上游 Parser/Analyzer 失败导致依赖检查没能运行。

它形成 Coverage gap；不能因为下游没有 Finding 就声称对象干净。

Evidence、RuleMatch、Finding 有什么区别？

Evidence 是字节事实，RuleMatch 是规则命中事件，Finding 是最终问题身份。

分层让同一证据可复用、同类命中可去重，并让历史 fingerprint 和报告位置稳定。

静态不执行 Skill，为什么还会有 subprocess？

subprocess 运行的是受信任的 Bandit/gitleaks 分析器，不是被审代码。

Verity 把快照字节暂存给工具扫描，再将受控结果映射成 Finding；不会安装或启动 Skill 自己的入口。

行为画像是什么？

对任务、runtime、输入输出、工具、状态、副作用和数据边界的证据化事实摘要。

它不是 Finding、不直接扣分，也不执行代码；它帮助动态 Planner 只选与 Artifact 相关的检查。

行为画像会猜测不存在的能力吗？

不会把没有证据的正向能力写进画像。

事实来自 manifest、文本模式和 Python AST；覆盖不足会留空或 unavailable，而不是用模型臆测补齐。

动态计划是什么？

把注册的动态检查逐项标为 selected、not_applicable 或 unavailable。

selected 只代表依据画像值得运行，不代表已经执行，更不代表通过。

语义、黑盒、沙箱与 Harness

语义审查怎么工作？

Candidate 提出受控候选，Validator 按固定策略和 Evidence 验证。

确认后才形成语义 Finding；完整 Prompt sweep 也按 Finding Type 独立调用，避免把大量类型塞进一次请求而稀释注意力。

模型可以发明新的 Finding Type 吗？

不可以，只能使用本地封闭目录中注册的类型。

响应 schema、subject taxonomy 和本地身份重派生会拒绝未知类型、字段与额外权限。

模型可以决定严重度吗？

不可以，严重度来自 Verity 的本地目录策略。

Validator schema 禁止 severity，最终投影也直接读取本地 Finding Type 定义。

为什么支持多个 Validator？

用独立模型多数票降低单一判断器偏差。

推荐 2–3 个总票源；Provider 失败不投票，意见打平不会被静默判成通过或拒绝。

Validator 投票打平怎么办？

返回 insufficient_evidence 并保留 vote_split 原因。

这把“模型意见冲突”与“所有模型都认为证据不足”区分开来，不强行选边。

语义审查和 Prompt 黑盒有什么区别？

语义判断受控证据；黑盒把完整 Prompt 交给真实模型执行场景。

二者 Provider、外发内容、预算和结论都独立；不能用语义的“脱敏证据”承诺描述黑盒。

Prompt 黑盒默认开启吗？

不，默认关闭。

Web 要启用加二次出站确认；CLI 要显式 --enable-prompt-blackbox 与完整 Provider/Key 环境变量配置。

artifact_aware 黑盒策略是什么意思？

根据行为画像只选择与该 Prompt 任务和契约相关的场景。

每个注册检查仍会记录 selected/not_applicable/unavailable 和理由；不是悄悄少跑。

当前有多少 Prompt 黑盒检查？

35 个映射组件：26 个通用场景，加 5 个导演/分镜和 4 个画风文本契约检查。

这只是注册规模；每个 Artifact 的实际选择取决于画像和适配器可用性。

画风检查能验证最终图像长得对不对吗？

不能；当前检查的是文本契约与 trace，不是渲染图像。

没有图像 Provider/evaluator 时，视觉保真度必须明确为 unavailable:image_runtime_not_configured。

为什么关闭可执行 Skill 沙箱？

旧 runner 尚未证明限制宿主读取、输出、磁盘、进程树和观察器篡改。

报告还可能泄露 exception/path/argv/SQL；在这些边界和真实 macOS 对抗测试完成前，产品必须失败关闭。

显式勾选或传参会执行 Skill 吗？

不会。当前请求在 import/construct research runner 前就失败。

Web 控件禁用，CLI 兼容参数只产生 sandbox_isolation_hardening_required 诊断。

Agent Harness 与 Skill 沙箱有什么区别？

Harness 模拟 instruction-only Skill 的 Agent 行为；沙箱原本面向可执行代码。

Harness 的工具无副作用，不能替代 host/process/network 隔离；两条路径的适用对象和结论完全不同。

Agent Harness 在 Web 里能开吗？

不能，仅 CLI。

增加 Web 启用面会扩大凭证、外部 DSH、Provider 和运行时边界，必须另做安全设计与审查。

Harness 会自动安装 DSH 吗？

不会。DSH 不 vendored，也不是 Python 依赖。

受信任调用方提供外部 Node/DSH 入口、SHA-256 和确切 0.1.1-rc.2；Verity 不改变全局环境。

Harness 的四个模型可见工具会产生真实副作用吗？

不会：内存合成读、阻断 HTTP、阻断 shell、拒绝审批。

attempt signal 表示模型尝试调用模拟工具，不表示主机文件被读、网络真的发送或命令真的执行。

Harness 会联网吗？

会；启用后 Skill 指令和 Scenario Prompt 会发送给真实 Provider。

模拟工具不产生 HTTP 副作用，但 DSH/Node 进程与 Provider 请求本身仍是真实边界。

Harness 是 OS / 进程 / 网络沙箱吗？

不是。

setsid() 后代可能逃出同 session 清理，两个入口哈希不认证相邻 npm 闭包，Provider 出站也没有目的地址隔离；强使用需要外层 container/microVM。

Harness 完成且没有信号，是否证明 Agent 安全？

不证明，只说明这次有界实验完成。

它不是通用 pass、跨 Agent 结论或已评测精度结果；未选择的场景和未模拟的工具仍然未知。

数据、安全与隐私

不配置 Provider 时会联网吗？

默认静态路径不会发 Provider 请求。

CLI 默认会“尝试”语义配置解析，但没有完整 Provider 时只记录 provider_not_configured；使用 --no-semantic 可明确关闭。

配置语义 Provider 后会发送什么？

受控 subject、位置、策略和 metadata；Web 可附短的脱敏 Evidence snippet。

敏感 Evidence 整条不发，字符串和位置有上限，主机路径会被剥离；完整 Artifact 出站模式没有实现。

Prompt 黑盒会发送什么？

完整被审 Prompt、固定 probe 和多轮前序回复。

实现始终把被审 Prompt 放在模型的 system role；这条路径不受语义 metadata/redacted-evidence 策略保护。

CLI 会把 API Key 放在参数里吗？

不会，只接受 API Key 的环境变量名。

Key 值在调用时解析，不进入序列化配置、报告、SARIF 或 process argv。

Web API Key 存在哪里？浏览器能读回吗？

只有保存的语义 Provider Key 进入当前 macOS 用户 Keychain；浏览器只能得到 keySaved 布尔值。

语义 URL/模型偏好存 owner-only JSON，审查时语义 Key 进入随机临时环境变量并在结束后清理；没有明文文件 fallback。Prompt 黑盒 Key 每次审查单独提供，只在临时环境变量中使用后清理，不持久化，也不复用语义 Key。

被审 Skill 能修改 Provider、模型或检查策略吗？

不能。

Artifact 只能提供被解析的事实；Provider、凭证、Scenario、严重度、预算、工具路径、处置和 phase gate 来自受信任调用方与本地注册表。

报告会保存原始 Secret 吗？

不会；gitleaks 结果在进入对象模型前就脱敏。

敏感性标记一直传到 Web 投影，页面不会从源码重新构造 Secret 预览。

项目历史会保存原始文件或 Provider 内容吗？

不会，只保存 allowlist 安全投影。

不保存 Artifact 原字节、Evidence 原文、Provider payload/response、API Key、RedactionMap、主机/临时/工具路径。

报告、分数、版本与门控

报告最重要的顶层字段有哪些？

coverage、behaviorProfile、dynamicPlan、findings、五项 capabilities、score、reviewConfidence、issues、verdict。

完整字段树见本手册“如何读懂报告”章节。

统一 Issue 是什么？

按稳定风险 ID 聚合静态、语义和运行时 occurrence 的视图。

它让同一根风险能横跨层对照，同时保留每个原始 Finding、Scenario、signal 和 Evidence 身份。

not_reproduced 表示静态问题被删除了吗？

不表示；静态 Finding 永远保留。

它只增加“相关有界动态检查本次没有复现”的观察，不能推翻静态事实或保证其它模型/配置也不复现。

安全分怎么计算？

把完成阶段的 occurrence 映射到统一风险，按严重度递减扣分并应用上限。

Critical/High/Medium/Low 基础扣分为 45/25/10/3，同一 root 后续为 50%、25%，分数上限分别 39/59/79/99。

分数 100 是否代表 100% 安全？

不代表，只表示已完成检查中没有扣分项。

未实现、未选择、不可用和当前 breadth 未覆盖的风险不可能靠这个数字消失。

什么时候没有数字分数？

Coverage 不足、映射不一致，或被请求的语义/黑盒/沙箱/Harness 未完成时。

unavailable 是诚实的“无法形成结论”，不是 0 分，也不是 100 分。

Review Confidence 与安全分相同吗？

不同。Confidence 说明结论证据条件，Score 说明完成检查中的风险扣分。

当前静态完整/语义未启用通常为 C，语义完成可到 B，失败为 D；A 因 breadth 未 evaluated 而不可达。

CLI 退出码 0 代表什么？

Coverage 足够且没有 High/Critical 阻断。

它不代表没有 Medium/Low，也不代表所有动态层启用或检测面已评测；查看报告 capability 与 gap。

CLI 退出码 1 代表什么？

至少一个 High/Critical Finding 或对应运行时 occurrence。

findings_block 优先于 coverage_block，所以即使同时有 Coverage 缺口仍返回 1。

CLI 退出码 3 代表什么？

Coverage 不足或显式/完整配置请求的关键阶段未完成，且没有 High/Critical。

它刻意避开 argparse 的退出码 2。

Medium / Low 默认阻断 CI 吗？

不阻断；默认 gate 只阻断 High/Critical。

Prompt 产品 Verdict 仍可能是 needs_revision，因为“需要改进”与“CI 是否硬阻断”是两套政策。

整改建议会自动修改代码或 Prompt 吗？

不会，applyMode=proposal_only。

Web 可编辑 Prompt 草稿并重新审查；Skill 只给有证据的 actions 和同范围复查项，没有自动 PatchSet apply。

接受风险或误报会修改严重度和原始分数吗？

不会，处置默认只是有期限的审阅注释。

只有 CLI 显式 --respect-dispositions 时，有效 accept_risk 才影响 High gate；原始证据和 Score 保留。

Skill 项目差异有哪五种状态？

new、existing、changed、resolved、unknown_due_to_coverage。

相关检查未完成时，旧问题消失只能是 unknown，不能被误报为 resolved。

覆盖与评测可信度

当前有多少统一风险和映射组件？

46 个统一风险、156 个运行时映射组件。

156 = 63 规则 + 1 capability extractor + 41 语义类型 + 35 黑盒 + 12 dormant 沙箱信号 + 4 Harness 信号。

completed 是否代表检测完整？

不代表，它只是本次阶段执行状态。

检测广度是另一条 none/signal/partial/substantial/evaluated 轴；当前没有任何风险达到 substantial/evaluated。

84 个 L0 合成案例上的高数字能当真实精度吗？

不能，那是每风险极少量刻意正例/安全对照的配对基线。

它适合检查回归与机械契约，不足以代表真实分布、长尾语言或对抗改写。

82 次语义合约回放证明什么？

证明 JSON schema、候选身份、投票和投影等流水线契约。

固定回放不调用真实模型，因此不能证明 Provider 的判断准确率。

为什么没有可引用的 Butler 优越性结果？

历史 Butler 运行健康度不足，标签和配对观察也不满足正式门槛。

比较器因此返回 not_eligible，不输出相对结论；拒绝产生数字本身是质量控制的一部分。

Verity 能完全代替人工安全审查吗？

不能。

它提供可复现证据、门控和优先级，适合持续审查与缩小人工范围；架构、业务授权、真实环境和未知攻击仍需人工与独立测试。

25 / 25 个术语
Artifact（被审对象）
一次审查的一个 Prompt 或一个 Agent Skill。它是输入，不是 Verity 自己的代码，也没有权配置审查环境。
ArtifactSnapshot（制品快照）
摄入后冻结的内容寻址元数据和内存字节集合；下游分析不回读原始目录。
Evidence（证据）
来自明确文件与 byte range 的受控事实。它不是模型主观理由，也不一定单独构成问题。
RuleMatchEvent（规则命中事件）
某个注册规则对 Evidence 的一次机械匹配，是从事实到 Finding 的中间层。
Finding（问题）
有稳定类型、subject、严重度、证据和 occurrence fingerprint 的可报告问题。模型不能自定严重度。
Issue（统一问题）
按统一风险 ID 聚合多个静态、语义、黑盒或运行时 occurrence 的报告视图；不会吞掉原始 Finding。
ReviewPlan（审查计划）
本次应该运行哪些确定性组件，以及它们的适用性和门控要求。
Coverage（执行覆盖）
计划中的关键检查是否完成。它不同于“检测广度”，也不同于代码覆盖率。
Detection breadth（检测广度）
对一个风险类别的实质检测能力等级：none、signal、partial、substantial、evaluated。当前最高只有 partial。
Provider（模型服务）
由受信任调用方配置的外部或 loopback 模型端点。被审 Artifact 不能选择它。
Candidate（语义候选）
由本地 extractor/catalog 或受控生成器提出、尚待 Validator 证实的 Finding 假设。
Validator（校验者）
只能看到候选、白名单 Evidence 和书面策略的独立判断者；可以用多 Provider 多数票。
BehaviorProfile（行为画像）
Artifact 的任务/runtime/数据/工具/状态/副作用事实摘要。它是适用性输入，不是漏洞列表。
DynamicPlan（动态适用性计划）
记录每个动态检查为何 selected、not_applicable 或 unavailable；selected 不等于 executed/pass。
Black-box（黑盒）
把完整 Prompt 交给真实模型按固定 Scenario 运行，再从输出判断行为。它会产生明确网络出站。
Sandbox（执行沙箱）
理论上约束可执行 Skill 的 host/process/network 边界；Verity 当前产品路径不可用，不能与 Harness 混称。
Agent Harness（指令运行时适配器）
CLI-only、默认关闭的 instruction-only Skill 模拟层，组合外部 DSH 与四个无副作用工具；不是 OS 沙箱。
Fail closed（失败关闭）
当隔离、配置、预算或输出不满足要求时返回失败/不可用，而不是继续运行或把未知当成 pass。
Redacted egress（脱敏出站）
只发送受控 metadata 和可允许的短 Evidence 片段；敏感 Evidence 整条不发，完整 Artifact 模式不存在。
Score（安全分）
完成检查中按风险/严重度计算的可解释扣分投影。100 不是安全保证，Coverage 不足时没有数字。
Review Confidence（审查置信度）
对本次结论证据条件的 A–D 标签；A 当前不可达，与模型置信度或安全分无关。
Verdict（主体判定）
在当前 Coverage 和 Findings 下，对 Prompt/Skill 的处置结论；不等同于 CLI process exit code。
Disposition（处置标记）
